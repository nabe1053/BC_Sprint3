# memory.md 運用規約（memory-protocol）

`.claude/memory.md` は実装ハーネスの**唯一の可変状態ハブ**（進捗・決定・知恵）。
設計書（`docs/requirements/`）が「変わらない WHAT」なのに対し、memory.md は「育つ HOW/進捗」。

## 編集責任

- **編集できるのは orchestrator 役（実装を指揮するメインセッション）だけ。**
  本プロジェクトは build-loop を使わず手動スライスループで実装するため、
  orchestrator 役 = 研修者と対話しているメインセッション（CLAUDE.md 決定事項5）。
- サブエージェント（test-designer / implementer / reviewer）は **読むだけ**。指摘・学びは戻り値で返し、orchestrator 役が追記する。
- これにより複数エージェント同時書込による破壊を防ぐ。

## 書式（セクション固定・追記型）

```markdown
# Project Memory  <!-- orchestrator が唯一の編集責任者 -->

## 1. アーキテクチャ決定 (ADR-lite)
- [AD-001] {決定}。理由:… / 影響範囲:…

## 2. 確立した規約・パターン
- [CV-001] {恒久ルール}

## 3. 実装バックログ（プラン状態＝ループの制御表）
| ID | スライス | 依存 | Status | レビュー | 最終更新 |
|----|---------|------|--------|---------|---------|
| S1 | … | -  | PLANNED | - | … |

## 4. レビュー指摘と対応履歴
- [RV-001] {ID}: {指摘} → {対応} → （必要なら §2 へ昇格）

## 5. 学び・ハマりどころ（再発防止）
- [LN-001] {気づき}

## 6. 未解決 / BLOCKED / TODO
- [BLK-001] {ID}: レビュー上限超過。原因:… / 残指摘:… / 要人手
```

## ID 採番

| 接頭辞 | 用途 | セクション |
|-------|------|-----------|
| AD | アーキテクチャ決定 | §1 |
| CV | 規約・パターン | §2 |
| RV | レビュー指摘 | §4 |
| LN | 学び | §5 |
| BLK | BLOCKED | §6 |

- 連番はセクションごとにゼロ埋め3桁（AD-001…）。既存の最大値+1 を採番。
- 一度採番した ID は**再利用しない**（追記型）。

## Status 語彙（§3 スライスのライフサイクル）

```
PLANNED → IMPLEMENTING → REVIEWING → FIXING → DONE
                                         └→（上限超過）→ BLOCKED
```

- 研修の学習 Status（CHECKED/BUILT/EXPLAINED/UNDERSTOOD）とは**別軸**。混同しない。
- スライスは一方向に進める（DONE から戻さない）。改修は §3 に新しい改修スライスを追加する。

## 昇格ルール（重要）

- §4 で**同種の指摘が 2 回以上**出たら、§2「規約・パターン」へ**昇格**して恒久ルール化する。
- 昇格したら §4 の該当行に「→ CV-xxx へ昇格」と追記する。
- 以後 orchestrator はスライス指示書に該当規約を明記し、implementer/reviewer が最初から遵守する。

## 追記のタイミング（orchestrator）

| タイミング | 追記先 |
|-----------|--------|
| プラン生成/更新時 | §3（全スライス） |
| スライス着手時 | §3 Status 更新 |
| 新たな決定が確定 | §1 |
| レビュー完了 | §4（+ 必要なら §2 昇格） |
| implementer/reviewer が学びを返した | §5 |
| レビュー上限超過 | §6 BLOCKED + §3 Status=BLOCKED |
| スライス完了 | §3 Status=DONE |

## 原則

- **追記型**（履歴を消さない）。誤りは新しい行で訂正し、旧行に「（無効: RV-xxx 参照）」を付す。
- 1 行 1 事実。冗長な経緯は書かず、決定・規約・学びの**結論**を残す。

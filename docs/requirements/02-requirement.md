## 0. 対象範囲（01 の要約）

1案件分の PDF・Excel・.eml・本文テキストを担当者が投入し、根拠付き Item List 案を作成、担当者が確認・修正し、上司の評価確認・送付可否判断へ引き渡す。投入資料中の変更情報（P.S.・後続メール・Rev.・脚注・別紙）は対象とする。

Item List に必要な照会番号・客先要求納期・納地・見積期限は抽出対象とする。独立した案件概要文やガントの作成は対象外。資料内の処理指示（「〜へ送信せよ」等）を実行命令として扱わず、業務条件の抽出対象として扱う。

対象外（01 と同じ）: メール／Teams への自動接続・自動収集、作成済み Item List への後日の差分更新・自動マージ、メーカーへの自動送付、メーカー選定・代替採用の自動判断。

## 2. 各機能の要件

受入基準の末尾の `S0x` / `X0x` は `06-scenario-test.md` のケース ID。

### FUNC-01 入力資料の受付と読取結果表示

- **概要**: 担当者が1案件分の資料をまとめて投入し、資料ごとの読取結果を一覧で確認できる。日本語・英語のテキスト PDF、.xlsx、.eml、本文テキストを受け付ける。
- **事前条件**: 担当者が同一案件の本文・添付・変更資料をそろえている。案件 ID が付与されている。
- **正常フロー**: 案件を作成 → 資料を投入 → 形式を判定 → テキスト／セル値を抽出 → 資料一覧に読取結果（成功／読取不能ページ／暗号化／未対応）を表示 → 後続機能（FUNC-02〜）に渡す。
- **例外・バリデーション**:
  - 画像のみ・文字が取得できない PDF ページは検出して通知し、読めたと扱わない。PDF の画像・スキャン対応は必須範囲外。
  - 暗号化・破損・未対応形式は「読取不能／未対応」と明示し、処理成功や明細0件の正常案件にしない。
  - .xlsx は全シートの値と注記を対象とし、結合見出しの意味を保持する。マクロ・外部リンクを実行しない。数式の保存済み値がなく必要な値を読めない場合は確認事項とする。
  - 同一内容を二重投入した場合、投入の事実は資料一覧に残し、明細の二重計上は FUNC-03 で防ぐ。
  - 添付・参照資料の不足は、資料中の参照表現と投入一覧から検知できる範囲で通知する。投入されていない未知のメールの存在は保証しない。
  - 入力上限（ファイル数・容量・ページ数）は D02 で確定する。上限内は切り捨てず処理し、超過は具体的に通知する。少なくとも現行10件を内容の切り捨てなく処理できること。
- **受入基準**:
  - sample-01〜10 の全資料を原形式（.eml 含む）で投入でき、いずれも切り捨てなく読取成功になる（S01〜S10）。
  - 画像のみ PDF・未対応形式・破損ファイルを投入すると、読取不能・未対応と対象範囲が通知され、成功扱いにならない（X01）。
  - 同一資料を二重投入しても資料一覧に両方の投入が残る（X03）。
  - 宣言した上限ちょうどは切り捨てなく処理、超過は具体的に通知される（X09。D02 未確定なら未実施と記録）。

### FUNC-02 メール構造の保持と前後関係の判定

- **概要**: .eml を直接投入し、本文・引用部・送受信日時・件名・添付一覧を保持する。P.S.・後続メール・転送時の注記による変更を、明示された訂正対象と内容の照合で判定する。
- **事前条件**: FUNC-01 で .eml または本文テキストが読取成功している。
- **正常フロー**: ヘッダ（From／Date／Subject）を取得 → 本文と引用部を分離 → 添付一覧を作成 → 本文中の変更表現（「〜ではなく」「was」「Rev.」「P.S.」）と対象明細を照合 → 変更候補を FUNC-06 に渡す。
- **例外・バリデーション**:
  - 引用の表示順だけで新旧を決めない。日時と明示された訂正対象を使う。
  - plain と HTML に同じ本文がある場合は二重抽出しない。HTML のみの場合も本文を読み取るが、外部画像・リンクを取得しない。
  - 添付は一覧を示すのみ。PoC では担当者が必要な添付を別ファイルとして投入し、その手作業時間は KPI に含める。
  - 本文テキストとして投入され日時・順序が判定できない場合は、変更を確定せず確認事項を出す。
  - 転送メールの転送者注記（「単価はまだ不要」「代替可否はメーカーに別途確認」）は判断事項として保持し、明細の値に反映しない。
- **受入基準**:
  - sample-04: P.S. により No.1 の数量 240→320 本が採用され、旧値と P.S. の根拠が記録される（S04）。
  - sample-10: 引用本文の item 1 240 本が最新本文で 300 本に訂正され、68# は追加見積候補として関連付けられる（S10）。
  - sample-07: 転送前の大久保注記が判断事項として保持され、3行目の材質は L80＋「13Cr 希望・代替提案可」のまま確定しない（S07）。
  - plain／HTML 同内容の試験メールで明細が二重計上されない（X03）。
  - 日時を欠いた本文テキストで相反する数量を与えると、両候補と確認事項が生成される（X04）。

### FUNC-03 明細抽出と出典保持

- **概要**: 資料全体（全ページ・全シート・別紙・脚注）から明細行を抽出し、原項番と出典（資料名・ページ／シート・セル／メール本文位置）を保持する。原資料との網羅性確認に使える明細一覧を作る。
- **事前条件**: FUNC-01 で読取成功した資料がある。
- **正常フロー**: 明細表の所在を特定（本文・別紙・複数ページ） → 行を抽出 → 原項番・品種・寸法・グレード・接続・レンジ・数量・単位・納期・備考を項目に分ける → 各項目に出典を付与 → 明細一覧を作成。
- **例外・バリデーション**:
  - 小計・合計・引用による再掲・参考換算（括弧内の概算 m／本）を独立明細にしない。
  - 数値と単位を分離する。TBA・記載なし・適用なしは状態として区別し、数値0や架空の仕様に変換しない。
  - 肉厚と単重、レンジと定尺長は別項目にする。クロスオーバーは両端の径・接続・BOX／PIN を保持する補足項目を持ち、単一径に潰さない。
  - 同一内容の二重投入・plain／HTML 重複からの明細は1回だけ計上する。
- **受入基準**:
  - sample-01: No.1〜12 の12行。No.9 は 3.0m・24本、No.11 は両端 9-5/8 VAM TOP × 13-3/8 BTC・8本、No.12 は 40個（S01）。
  - sample-02: 6行のみ。小計 380・46、合計 426 を明細にしない（S02）。
  - sample-05: p5〜6 の12項目を漏らさない（S05）。
  - 10件の期待行数合計 73 行（択一分割は FUNC-06）が、正解表と原項番で対応付けられる（S01〜S10）。
  - 二重投入しても同じ明細が二重計上されない（X03）。

### FUNC-04 共通条件と個別例外の適用

- **概要**: 本文・条件欄に書かれた案件共通の条件（納期・納地・受渡条件・標準接続・レンジ・適用規格）を各明細に適用し、明細側・特記事項・脚注の個別例外を優先する。共通条件を明細に適用した場合も根拠を追跡できる。
- **事前条件**: FUNC-03 で明細一覧と出典がある。
- **正常フロー**: 共通条件を抽出 → 各明細の個別記載を確認 → 個別記載があれば優先、なければ共通条件を適用 → 適用元（共通／個別）と出典を根拠に記録。
- **例外・バリデーション**:
  - 単に記載場所が後という理由で上書きしない。明示された適用対象・優先関係に従う。
  - 変更対象や優先関係が判定できない場合は、両候補を保持し確認事項にする。
  - 「本文3.2項による」等の参照先が投入資料内に無い場合は参照不足を表示し、推測で確定しない。
  - 見積提出期限（回答期限）と客先要求納期を混同しない。両方を別項目で保持する。
  - 条件文中の接続名の列挙（例: 「Premium connections (VAM TOP / VAM 21) to be threaded by…」）を、明細の択一指定と誤認しない。
- **受入基準**:
  - sample-03: 共通 VAM TOP・R3 に対し No.5 のみ BTC、No.4 のみ R2。共通納期 2027年3月末・新潟東港渡しが全行に適用され、回答期限 2026年8月7日は納期にならない（S03）。
  - sample-05: No.3／4 の接続が p4 3.2項参照で VAM TOP。納期は各行の 4／5／6 月。見積期限 8月21日17時は別項目（S05）。
  - sample-09: p3 の VAM TOP／VAM 21 記載を追加の択一指定と誤認しない（S09）。
  - p4 を除いた sample-05 コピーで参照不足が表示され、No.3／4 の接続を推測確定しない（X02）。
  - 優先関係を判定できない相反数量で両候補・出典・確認事項が残る（X04）。

### FUNC-05 表記・単位の整理と原表記保存

- **概要**: 4章の規則 R01〜R05 に従い、品種・単位・グレード・接続・レンジの表記差を整理し、原表記を必ず保存する。
- **事前条件**: FUNC-03 で項目分割された明細がある。承認済みの換算規則（D03）が無い場合は換算しない。
- **正常フロー**: 各項目の原表記を保存 → R01〜R03 の明確な表記差のみ整理 → 整理後の値と原値を根拠に対で記録。
- **例外・バリデーション**:
  - 未承認の仕様同等化（HCL80→L80、SM95TT→L80、13CR-95→13Cr-L80 等）を行わない。13Cr 等の材質修飾を落とさない。
  - 重量（t／MT）から本数を推定しない。mm 実測表記を公称 inch へ丸めない。肉厚から単重、レンジから平均長を推定しない。長さ範囲（10.4〜14.6m）を無断で R3 に変換しない。
  - 括弧内の概算本数・概算長は参考値として主数量と同時に保持し、置換しない。
  - 追加の換算値は、換算表・精度・丸めが承認（D03）された後のみ出力する。
- **受入基準**:
  - sample-02: 原数量 118／152／76／34／28／18 t と外径 mm・肉厚 mm・長さ範囲を保持し、本数を確定せず換算条件不足を示す（S02）。
  - sample-07: 2行目の 10.4〜14.6m を R3 に変換しない。3行目の 13Cr を確定材質にしない（S07）。
  - sample-08: Item 4 は 150 MT を主数量、約1,150本を参考値として保持（S08）。
  - sample-10: item 2 の HCL80 を L80 に自動置換しない（S10）。sample-06: SM95TT を L80 に置換せず代替提案可を記録（S06）。
  - 全10件で、整理後の値に対して原表記が根拠に残る（S01〜S10）。

### FUNC-06 変更・代替・択一・未確定の管理

- **概要**: 数量変更・明細追加・仕様変更は変更前後の値と採用根拠を記録する。代替・択一は候補ごとに行を持ち、選択グループ ID で関連付ける。TBA・未確定を状態として保持する。
- **事前条件**: FUNC-02（変更候補）、FUNC-04（優先関係）、FUNC-03（明細）の結果がある。
- **正常フロー**: 変更候補を対象明細に対応付け → 前後関係が明確なら採用し、旧値・新値・根拠・理由を記録 → 択一・追加見積候補は R06〜R08 に従い行分割し、同一グループに所属させる → 未確定は状態として保持。
- **例外・バリデーション**:
  - TBA を 0 や推定値に置換しない。
  - 択一候補の数量を合算して発注数量と表示しない。
  - 「代替提案可」という条件だけでは架空の代替行を生成しない。明示された追加見積候補（両方見積のこと、alternate quote）のみ行化する。
  - 追加候補の省略仕様（sample-10 の 68#）は無条件に確定せず、原明細からの継承候補と確認事項を示す。
  - 前後関係が明確でない変更は反映せず、候補として保持する（FUNC-04 と同じ）。
- **受入基準**:
  - sample-06: 原8項目を11行に分割。No.4 は VAM TOP／VAM 21 各260本、No.5 は各380本の択一。No.7 は 5FT×6本と 10FT×6本。No.6 の TBA を保持（S06）。
  - sample-08: Item 3 は Rev.2 により 180→240 本に訂正。Item 6 は追加明細として1回だけ抽出。5a／5b 各280本は択一グループ（S08）。
  - sample-10: 72# 原案と 68# 候補は各300本で択一、計600本としない（S10）。
  - sample-04: 240→320 本の旧値・新値・根拠が記録される（S04）。
  - TBA を保持した出力は正解になり得るが、0 に変更した出力は数量誤りとして採点される（X05）。

### FUNC-07 根拠と確認事項の提示

- **概要**: 重要項目（品種・数量・単位・外径・肉厚／単重・グレード・接続・レンジ・客先要求納期・納地・変更事項）ごとに出典・換算条件・変更理由を表示する。不明・矛盾・参照不足・代替判断・条件不足を確認事項一覧にし、対象行・対象項目・理由・候補／不足条件を示す。
- **事前条件**: FUNC-03〜06 の結果がある。
- **正常フロー**: 各項目の根拠（原値・採用値・資料名・位置・引用箇所・共通／個別・換算条件・変更理由）を組み立て → 確認が必要な箇所を確認 ID 付きで一覧化 → 警告行として明細に紐付け。
- **例外・バリデーション**:
  - 根拠の無い採用値を出力しない。根拠を付けられない値は確認事項にする。
  - 確認事項は「行 ID または案件 ID」「対象項目」「理由」「候補・不足条件」を必ず持つ。
  - 警告が無いことを正確性の保証として表示しない。
- **受入基準**:
  - 全10件で、全明細の重要項目に出典（資料名＋ページ／シート・セル／本文位置）が付く（S01〜S10）。
  - sample-02: 本数換算に必要な条件不足が確認事項になる（S02）。
  - sample-05: 25Cr 系の同等材提案可、No.11 の寸法詳細未確定が確認事項になる（S05）。
  - sample-07: 上司の代替確認予定が判断事項として保持される（S07）。
  - sample-10: Friday COB の時刻帯不足が確認事項になる（S10）。
  - 参照不足（X02）・相反数量（X04）で確認事項が対象行・対象項目付きで生成される。

### FUNC-08 担当者確認・修正記録と引合書承認

- **概要**: 担当者が値と出典の一致確認、明細一覧の網羅性確認を行い、修正前後・修正理由・確認結果を**アプリ内で**記録できる。上司には引合書承認画面（`03-spec` SCR-06）で、確定した Item List そのものを提示する。あわせて **①確認結果の件数（一致確認 n/N・網羅性確認・訂正・未解決・差し戻しコメント）は常に見える状態にし、②修正箇所・変更／判断事項・未解決事項の一覧には1操作で到達でき、③表の行から、その行に紐づく変更／判断事項・未解決事項へ到達できる**ようにする。一覧を画面に常置するかドロワーで開くかは画面の設計に委ねる（`03-spec` SCR-06）。ただし件数を隠さないこと、行に紐づかない案件レベルの事項の存在が行単位の表示でも分かることを条件とする。旧名称「担当者確認・修正記録と上司向けサマリ」。サマリを別に読むのではなく、確定した表を見て承認する形に変えたため改称した。
- **編集の範囲**: 自由なセル編集ではなく「対象項目を選ぶ → 新値を入力 → 修正理由を入力」の1操作に限定する。これにより 5章・6章の制約（数値と単位の分離、TBA・記載なし・適用なしの状態、択一グループの整合、原表記の保持）を編集後も守る。原表記・出典は編集対象にしない。
- **事前条件**: FUNC-07 の根拠付き案がある。担当者・上司の役割が記録される（同一人物の研修では役割ごとに操作・時間を区別）。
- **正常フロー**: 担当者が警告行を優先確認 → 全行の重要項目を出典と一致確認 → 原資料の明細一覧と突合して欠落・重複を確認 → 修正（前後値・理由）と確認結果を記録 → 引合書承認画面に確定した表と件数を表示し、一覧へ到達できる状態にする → 上司が行または一覧から判断が必要な箇所を確かめ、判断を記録。
- **例外・バリデーション**:
  - 確認者名・確認日時は実在の確認者の操作から記録する。AI が承認者名や日時を作らない。
  - 修正は旧値を上書きせず、旧値・新値・理由を残す。
  - 修正理由が空の場合は記録しない。修正者・確認者は入力必須とし、AI が補完しない。
  - 編集によって単位のない数量、状態のない未確定、択一グループの数量合算などを作れないようにする。
  - 未解決事項が残る場合、引合書承認画面の要約と未解決事項一覧に件数つきで明示する。
- **受入基準**:
  - sample-08 の Item 3 を担当者がアプリ内で修正し上司が確認すると、旧値・新値・理由・確認結果が残り、AI が確認者や日時を捏造しない（X06）。
  - TBA 保持のまま担当者確認・上司確認を通せる（X05）。
  - 引合書承認画面で、担当者の一致確認・網羅性確認・訂正・未解決の完了状況が**件数で常に見える**（X05, X06）。
  - 「修正箇所」（行ごとの担当者の訂正）、「変更・判断事項の一覧」（P.S.採用・Rev.訂正・択一・TBA・継承候補・担当者の訂正・判断のある行）、「未解決事項の一覧」（行単位と案件レベル）に**1操作で到達**できる（X05, X06）。
  - 表の**行から、その行に紐づく**変更／判断事項・未解決事項に到達できる。事項が無い行では「原資料との照合は必要」である旨が示され、確認済みと混同されない。行に紐づかない案件レベルの事項があるときは、行単位の表示でもその存在が分かる（X05）。
  - 上司は全行を並べた表を「変更・判断事項のある行」「訂正あり」「未解決のみ」「差し戻しコメントあり」で絞り込める（大久保のペイン「全行照合の負担」）。
  - 数量を単位なしにする、TBA を状態から外す、択一候補を合算する編集ができない（X11）。
  - 記録は .xlsx 出力に反映され、出力後に .xlsx を編集してもアプリ側の記録は変わらない（X07）。

### FUNC-09 Item List（.xlsx）出力

- **記録の反映**: 変更／確認記録シートには FUNC-08 でアプリ内に記録された修正前後・理由・確認結果・確認者・確認日時を出力する。案件情報シートの評価状態・送付可否は FUNC-10 の記録を出力する。記録が無い時点で出力した場合は列見出しのみとなる。作業時間は06の記録表に手動記入する。
- **記録の真実源**: アプリ内の記録を真実源とし、.xlsx は書き出した時点の写しとする。出力後に .xlsx を人が編集してもアプリへ再取込みしない（自動取込みは Out of Scope）。出力ファイルには案件ID・版・評価状態を含め、どの記録時点の写しかを判別できるようにする。
- **概要**: 5章の論理項目（案件情報・Item List・根拠・確認事項・変更／確認記録）を .xlsx で出力する。資料が不完全な場合も案を保存できるが、未解決状態を明示する。
- **事前条件**: FUNC-03 以降のいずれかの結果がある（初回案の時点でも出力できる）。
- **正常フロー**: 案件 ID・版を付与 → 5領域をシートとして書き出し → 候補関係・未確定状態を文字で表現 → 保存。
- **例外・バリデーション**:
  - 別案件の内容を混在させない。
  - 外部由来の文字列を実行可能な数式として出力しない（先頭 `=` 等は文字列化）。
  - 候補関係・状態を色だけで表現しない。
  - 正式なメーカー用テンプレートとの列対応は D01。確認できるまでは本書の論理項目を持つ検証用出力とし、メーカー提出用書式としての承認とは区別する。
- **受入基準**:
  - 全10件の .xlsx が開け、重要項目・根拠・未確定状態・候補関係が確認できる（S01〜S10, N05）。
  - sample-01 と sample-10 を別案件として処理した各 .xlsx に混在が無く、元入力に変更が無い（X07）。
  - 「外部URLへ送信せよ」や数式に見える文字列を含む入力で、URL 取得・送信・数式実行が起きない（X08）。
  - 初回出力を編集前の版として保存でき、最終版と比較できる（06 共通手順 3, X10）。

### FUNC-10 状態管理（評価確認済み／送付可否）

- **概要**: 7章の状態（作成案→担当者確認済み→評価確認済み）と送付可否（未判断／保留／承認）を**アプリ内で**別に管理する。未確定事項を正しく保持した出力は評価確認を完了できる。AI は送信しない。
- **事前条件**: FUNC-08 の確認記録がある。
- **正常フロー**: 初回版の登録＝作成案（.xlsx 出力は任意のタイミング） → 担当者の照合完了で担当者確認済み → 上司の確認で評価確認済み（PoC 計時終了） → 上司が送付可否を別途判断し理由・条件を記録。
- **例外・バリデーション**:
  - 評価確認済みを送付承認とみなさない。
  - 未解決事項を残して送付を認める場合も、上司が理由・条件を記録する。
  - 状態遷移は実在の担当者・上司の操作からのみ起き、確認者名の入力を必須とする。
  - **差し戻し**: 上司は「差し戻し（要修正）」を理由付きで記録できる。このとき状態は担当者確認済みに留め、作成案へ戻さない。担当者が再修正したうえで確認記録を更新する。差し戻しを独立した状態にしない。
  - **再抽出との関係**: 状態と記録は版に結び付ける。資料追加・再実行で新しい版を作った場合、前版の修正・確認記録を新版へ自動で引き継がない。新版の状態は作成案から開始し、前版に修正・確認記録がある場合は「前版の記録は引き継がれていない」旨を表示する（自動マージは Out of Scope）。
- **受入基準**:
  - TBA を保持した sample-06 が評価確認済みになれる。0 に変更した版は誤りとして採点され、評価確認と送付承認が区別される（X05）。
  - 状態・確認者・日時がアプリ内に記録され、.xlsx の案件情報・変更／確認記録に出力される（X06, X07）。
  - 確認者名を入力せずに状態遷移できない（X06）。
  - 修正・確認記録がある版に対して再実行すると、新版は作成案から始まり、記録が引き継がれていない旨が表示される（X12）。
  - 上司の差し戻しを記録しても状態は担当者確認済みに留まり、理由と判断者が残る（X13）。

## 3. スコープ

初版は以下の区分で実装する。**修正・確認・状態管理はアプリ内で完結させる**。.xlsx は作業の場ではなく、メーカーへの引合と記録の写しを書き出す成果物とする。

当初は FUNC-08／10 を Scope 2 に回し、初版では .xlsx を人が直接編集する案としていた。次の理由で初版に含める方針へ変更した。

- アプリの状態と .xlsx の状態が二重管理になり、どちらが最新かを人が管理する必要がある
- 案件一覧の進捗（担当者確認・上司の評価確認）を判定できず、一覧で進行状況が分からない
- 初回版の保全が .xlsx の別名保存に依存し、上書き1回で KPI（介入割合）の測定根拠を失う
- .xlsx のセル編集では 5章・6章の制約（TBA を 0 にしない、原表記を保持する、択一を合算しない、数値と単位を分離する）を人が破れる。アプリ内編集なら UI で守れる
- 資料追加後の再抽出、上司の差し戻しについて、アプリが記録を持たないと状態として扱えない
- 04-db で変更・確認記録を持つ以上、書き込み機能を持たない合理性が乏しい

| 区分 | 意味 |
|------|------|
| **Scope 1（初版）** | まず必ず作る。MVPとして成立させる最小機能 |
| **Scope 2（改善）** | 初版の次に着手する改善・拡張機能 |
| **Scope 3（余裕があれば）** | 時間・リソースに余裕があれば実装する機能 |
| **Out of Scope** | 今回は明確に実装しないと決めたもの |

### Scope 1（初版）

「引合書類を投入 → 根拠付き Item List 案 → 担当者の確認・修正 → 上司の評価確認 → .xlsx 出力」までを一気通貫で成立させる最小構成。S01〜S10 の抽出・出力の期待結果と、人の確認・修正・状態記録をこの範囲で満たし、06のScope 1受入条件で判定する。

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| FUNC-01 | 入力資料の受付と読取結果表示 | テキスト PDF・.xlsx・.eml・本文テキスト。上限（D02）は開発時に仮値を明示し、初版受入前に確定。上限内処理・超過通知・X09を初版に含む |
| FUNC-02 | メール構造の保持と前後関係の判定 | 01 が .eml 直接投入を要求。S04／S07／S10 が依存 |
| FUNC-03 | 明細抽出と出典保持 | 全機能の土台 |
| FUNC-04 | 共通条件と個別例外の適用 | S03／S05／S09 が依存 |
| FUNC-05 | 表記・単位の整理と原表記保存 | R01〜R05 の「整理」のみ。承認済み換算（D03）は Scope 3 |
| FUNC-06 | 変更・代替・択一・未確定の管理 | S04／S06／S08／S10 が依存 |
| FUNC-07 | 根拠と確認事項の提示 | 出典が無い Item List は要求を満たさないため初版に含む |
| FUNC-08 | 担当者確認・修正記録と引合書承認 | アプリ内で 一致確認・網羅性確認・修正（対象項目・新値・理由）・確認事項の判断を記録し、引合書承認画面に確定した表と件数を常時表示し、変更／判断事項・未解決事項の一覧へ1操作で到達できる（行単位の到達を含む）。編集は「項目選択＋新値＋理由」に限定 |
| FUNC-09 | Item List（.xlsx）出力 | 5領域のシートを出力。変更／確認記録と評価状態・送付可否は FUNC-08／10 の記録を反映。記録前は列見出しのみ、評価状態は作成案・送付可否は未判断で初期化 |
| FUNC-10 | 状態管理（評価確認済み／送付可否） | 作成案→担当者確認済み→評価確認済みの遷移、送付可否、確認者・日時をアプリ内で記録。確認者名は入力必須。差し戻しは状態を増やさず理由付きで記録。版をまたぐ記録の自動引き継ぎはしない |

### Scope 2（改善）

初版で修正・確認・状態管理はアプリ内で完結する。Scope 2 では、初版で人手に残る比較・引き継ぎ・分析を扱う。

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| FUNC-09 拡張 | 版の差分表示 | 初回案と修正版、再実行版どうしを原項番・候補・長さで対応付け、変更・追加・欠落・分割を区別して表示。初版は版を別に保持して人が比較する |
| FUNC-08 拡張 | 前版の修正・確認記録の引き継ぎ支援 | 再抽出した新版へ、前版の修正・判断を候補として提示する（採用は人が判断）。初版は「引き継がれていない」旨の表示のみ。自動マージは Out of Scope のまま |
| FUNC-08 拡張 | 作業時間の自動計測 | 準備・確認・修正・上司確認の所要時間をアプリで計測。初版は06の記録表へ手動記入 |
| FUNC-10 拡張 | 確認済み状態による絞り込み・集計 | 案件一覧での状態フィルタ、案件横断の未解決集計 |

### Scope 3（余裕があれば）

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| FUNC-05 拡張 | 承認済み換算の出力（トン→本数、mm→公称 inch 等） | D03（換算表・精度・丸め）承認後のみ。承認前は「換算しないこと」を評価 |
| FUNC-01 拡張 | 大容量への拡張・追加の負荷試験 | 初版の上限定義・超過通知・X09はScope 1。初版を超える容量・同時負荷への対応を後続とする |
| FUNC-01 拡張 | PDF 画像・スキャンページの読取 | 今回の必須範囲外の追加機能。承認待ち機能とは区別する。初版は読取不能箇所の検出・通知のみ |

### Out of Scope（今回は実装しない）

| 項目 | 実装しない理由 |
|------|----------------|
| メール／Teams への自動接続・自動収集 | 01 で対象外。資料収集と同一案件の確認は担当者の責任 |
| 作成済み Item List への後日の差分更新・人が修正した既存版との自動マージ | 01 で対象外。投入時点の資料に含まれる変更のみ対象 |
| 出力した .xlsx の編集内容をアプリへ取込むこと | 記録の真実源はアプリ内。.xlsx は書き出した時点の写しとし、双方向同期はしない（FUNC-09 記録の真実源） |
| メーカーへの自動送付・送信 | 01 の原則「対外送付可否は人が判断」。AI は送信しない |
| メーカー選定・代替品採用の自動判断 | 01 の原則「AI が業務判断を代行しない」。判断事項として提示するまで |
| 独立した案件概要文・スケジュール（ガント）の作成 | 01 で「引合情報読み込み」を対象外に限定。Item List に必要なヘッダ情報のみ抽出 |
| 認証・認可・マルチユーザー | ローカル単一利用者の PoC（4章）。担当者・上司・業務責任者は記録上のラベルであり、確認者名は入力による自己申告。本人性の検証・権限制御は行わない |

## 4. 非機能要件

| カテゴリ | 要件 | ID |
|----------|------|----|
| 性能 | 1案件（現行10件で最大: sample-05 の7ページ・12明細＋添付）の初回案生成を **10分以内**（仮置き）。AI 待ち時間は人の作業時間に含めず経過時間として別計測し、速度のために確認を省略しない | N06 |

| ユーザビリティ | .xlsx が開け、重要項目・根拠・未確定状態が確認できる。候補関係を色だけで表現しない。確認事項は対象行・対象項目を示す。外部由来の文字列を実行可能な数式として出力しない | N05 |
| 保守性 | 表記・換算規則（R01〜R08）を設定として分離し、使用した実装・モデル／設定・変換規則・入力版・出力版を評価記録に残す。同じ入力で結果が変わる場合、再実行結果を上書きせず比較可能にする | N04 |

## 5. 出力データ（論理項目）

以下を PoC の論理項目とする。正式な既存テンプレートが確認できるまでは、下記項目を持つ .xlsx を検証用出力とする。メーカー提出用書式としての承認とは区別する（D01）。列の並び・見せ方は `03-spec`、テーブル設計は `04-db` で定義する。

| 出力領域 | 必須で保持する項目 |
|----------|-------------------|
| 案件情報 | 案件ID、資料一覧、照会番号（存在時）、客先名、要求納期の原文・粒度、納地・受渡条件、見積期限の原文・日時条件、評価状態、送付可否 |
| Item List | 行ID、原項番、品種・用途、外径と単位、肉厚と単位、単重と単位、グレード、接続、レンジ、定尺長と単位、数量と単位、要求納期・納地、備考、選択グループID、候補区分、未確定状態 |
| 根拠 | 行ID、項目名、原値、採用値、資料名、ページ／シート・セル／メール本文位置、引用箇所、共通条件・個別例外、換算条件、変更の採用理由 |
| 確認事項 | 確認ID、行IDまたは案件ID、対象項目、理由、候補・不足条件、対応状況、判断内容・判断者 |
| 変更・確認記録 | 行ID、変更前後、変更理由、担当者の一致確認・網羅性確認結果、上司判断、確認者、確認日時 |
| 原明細インベントリ | 版ID、資料側の位置（ページ／シート・セル／本文位置）、原項番、原文抜粋、対応する行ID（0〜n件）、状態（対応済み／分割: 種別／除外: 種別／対応なし）、除外理由・分割根拠 |

原明細インベントリは、抽出時に資料側の全要素（明細にした行と、小計・合計・共通条件・変更指示・注記・脚注・署名など明細にしなかった要素）を除外理由つきで棚卸しした一覧である。網羅性確認（FUNC-08、`03-spec` SCR-05）のデータ源で、`agent-plan` の `record_source_inventory` が作る。**.xlsx の出力シートには含めない**（出力は上記5領域の5シート）。網羅性確認の証跡として .xlsx に残すのは、確認者・確認日時（変更・確認記録シート）と「網羅性確認 済／未」（案件情報シート）のみとする。インベントリ本体はアプリ内に版と結び付けて保持し、必要なら SCR-05 で参照する。テーブル設計は `04-db` で扱う。

- 数量等の数値と単位を分離する。TBA・記載なし・適用なしは状態として区別し、数値0や架空の仕様に変換しない。
- 肉厚と単重、レンジと定尺長は別項目にする。クロスオーバーは両端の径・接続・BOX／PIN を保持できる補足項目を設け、単一径に潰さない。
- 月・四半期・期間・月末の納期を原文の粒度で保持する。「2027年2月」を任意の日に変換しない。納期基準の荷揚／船積が不明なら不明とする。見積期限「Friday COB」は時刻・タイムゾーンを勝手に補わない。
- 納地等が記載されない資料では記載なしとする。全サンプルに照会番号・納地・見積期限があるとは仮定しない。

## 6. 表記・換算・明細分割規則

| ID | 規則 | 適用機能 |
|----|------|----------|
| R01 | CSG/Casing→ケーシング、TBG/Tubing→チュービング、PUP JT/Pup joint→パップジョイント、XO→クロスオーバー、CPLG→カップリング。Liner はライナーとして用途を残す。導管も区別する。原品名を併記する | FUNC-05 |
| R02 | JTS/jts→本、PCS/pcs→個、MT→メートルトン。資料中の単位注記を優先する。t は資料の質量表記を保持する。#・ppf は単重欄の文脈を確認して lb/ft として保持する | FUNC-05 |
| R03 | K-55/K55、L-80/L80、P-110/P110、R-2/R2、R-3/R3、VAMTOP/VAM TOP などの明確な表記差のみ整理する。HCL80、SM95TT、P110HP、13CR-95 等を他仕様へ置換しない。13Cr 等の材質修飾を落とさない | FUNC-05 |
| R04 | 原単位・数値を必ず保持する。追加の換算値は換算表・精度・丸めの承認（D03）後のみ出力する。mm の実測表記を公称 inch へ丸めたり、肉厚から単重、レンジから平均長、本数を推定しない。sample-02 は本数換算に必要な条件不足として質量を保持する | FUNC-05 |
| R05 | 括弧内の概算長・概算本数は参考値とし、主数量を置換しない。例: 150 MT と約1,150本は同時に保持するが、本数確定とはしない | FUNC-03, FUNC-05 |
| R06 | 独立して見積が必要な長さ・接続候補は別行にする。原項番から派生した行IDを付ける。sample-06 の 5FT と 10FT は各6本の2行、接続の択一候補も各1行とする | FUNC-06 |
| R07 | 択一候補は同一グループに所属させ、候補数量を合算して発注数量と表示しない。代替提案可という条件だけでは架空の代替行を生成しない。明示された追加見積候補のみ行化する | FUNC-06 |
| R08 | sample-10 の 68# 候補は、対象 item 1・変更後数量 300本との関連を保持する。材質等の省略条件は無条件に確定せず、原 item 1 からの継承候補と確認事項を示す | FUNC-06, FUNC-07 |

## 7. 確認と状態

下表は業務上の状態を示す。Scope 1 で担当者・上司がアプリ内に確認者・確認日時・判断理由とともに記録し、.xlsx 出力へ反映する。状態と記録は版に結び付け、版をまたいで自動で引き継がない。

| # | 状態 | 意味 | 到達条件 | 担当機能 |
|---|------|------|----------|----------|
| 1 | 作成案 | 抽出結果・出典・確認事項・原明細インベントリがアプリ内の版として登録された初回版。.xlsx 出力は状態の条件ではなく、担当者が任意のタイミングで行う | FUNC-01〜07 の完了（`agent-plan` の `finalize_draft` により版が登録された時点） | FUNC-07 |
| 2 | 担当者確認済み | 全行の重要項目を出典と照合し、原資料の明細一覧との突合で欠落・重複を確認した。矛盾・根拠不足のみ周辺文脈を追加確認 | 担当者の確認記録 | FUNC-08 |
| 3 | 評価確認済み | 上司が照合結果・修正・変更／判断事項を確認した。原資料自体の TBA 等が正しく記録されていればこの状態にでき、PoC の計時を終了できる | 上司の確認記録 | FUNC-10 |
| — | 差し戻し（要修正） | 上司が再修正を求めた記録。状態は 2 に留め、作成案へ戻さない。理由・判断者・日時を残す | 上司の判断記録 | FUNC-10 |
| — | 送付可否 | 「未判断／保留／承認」を状態 3 とは別に記録する。未解決事項を残して送付を認める場合も、上司が理由・条件を記録する。評価確認済みを送付承認とみなさない | 上司の判断記録 | FUNC-10 |

担当者と上司が同一人物の研修では、役割ごとの操作・所要時間を区別して記録する。承認済みとは実在の確認者が判断を記録した状態であり、AI が承認者名や日時を作らない。

.xlsx を出力した後にその .xlsx を人が編集しても、アプリ内の状態・記録は変わらない。出力ファイルは書き出した時点の写しであり、案件ID・版・評価状態で対応を判別する。

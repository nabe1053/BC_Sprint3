## 0. 前提：エージェントの担当範囲

FUNC-01〜10 のうち、**エージェントが担うのは FUNC-02〜07**（読取・抽出・条件適用・表記整理・変更管理・根拠と確認事項の提示）。前後は人とアプリの仕事であり、エージェントに渡さない。

| 範囲 | 担当 | 理由 |
|------|------|------|
| FUNC-01 資料の受付・形式判定・テキスト抽出 | **アプリ（決定的コード）** | 形式判定と抽出はLLMの判断を要しない。エージェントには `read_document` 等のツールとして提供する |
| **FUNC-02〜07 明細抽出・条件適用・表記整理・変更管理・根拠と確認事項** | **AGENT-01** | 資料ごとに構造が違い、どこを読むか・何を確認事項にするかが実行時の判断になる |
| FUNC-08 担当者の一致確認・修正記録 | **人（SCR-03／SCR-04）** | 01 の原則「AIが業務判断を代行しない」。AIは確認者名・日時を作らない |
| FUNC-09 .xlsx 出力 | **アプリ（人の操作）** | 記録の写しを書き出す決定的処理。エージェントは呼ばない |
| FUNC-10 状態管理・送付可否 | **人（SCR-03／SCR-06）** | 01 の原則「対外送付可否は人が判断」。AIは送信しない |

エージェントの成果物は **状態「作成案」の1版** であり、それ自体は完成品ではない。完成は上司の評価確認（人）をもって定義される（01 KPI）。

## 2. AGENT-01 引合明細抽出エージェント

### Part 1: エージェントの定義（基本設計）

> プロダクト定義レビュー（`/design-product-check`）の対象。

#### ミッション

**渡辺（引合担当）が引合書類を1行ずつ Excel に転記している作業を代行する。** 投入された資料を読み、メーカーへ出す Item List の明細行を、**1項目ごとに出典を付けて**組み立てる。読めない・足りない・矛盾する箇所は、勝手に埋めずに確認事項として対象行つきで差し出す。

代行しないこと: 値の正しさの最終判断、代替品の採否、換算の実行、対外送付。これらは人が決める（01 の原則）。

**対応機能(②)**: FUNC-02, FUNC-03, FUNC-04, FUNC-05, FUNC-06, FUNC-07

#### 登録・自己点検の進め方（AD-021）

- 材質・接続の代替候補は明細行にしない。`record_question` に対象行つきで残す（R03/R04）。原資料が明示する択一・分割（R06/R07）は区別する。
- 根拠・確認事項は項目を集め、`evidences` / `questions` の配列で一括登録する（1件でも配列）。
- `validate_draft` の違反はまとめて直してから再検証する。
- `propose_items` は1回で全行を登録する。

#### インプット

| 項目 | 内容 |
|------|------|
| 起動トリガー | 担当者の操作（SCR-02 の「案を作成」）。自動起動・定期実行はしない。既存版があっても上書きせず新版として起動する（N04） |
| 入力データ | ①案件ID配下の投入済み資料（テキストPDF・.xlsx・.eml・本文テキスト）とその読取結果 ②表記・換算・分割規則 R01〜R08（設定として分離／N04） ③出力データの論理項目定義（02 5章） |
| 渡すもの | 資料の本文・表・注記・脚注・メールヘッダと引用部の構造、資料一覧と読取状態、R01〜R08、案件ID・版ID |
| 渡さないもの | **他案件の資料・明細**（N01 の混在防止）、過去版の修正・確認記録（自動引き継ぎはしない／Out of Scope）、正解表（`06-scenario-test.md` の期待結果）、提案書・実業務資料・認証情報（D05 の除外対象）、担当者・上司の氏名 |

**コンテキスト方針の理由**: 過去版の記録を渡すと、前版の人の修正を「正解」として模倣し、抽出そのものの品質を測れなくなる（KPI の介入割合が測定不能になる）。正解表を渡さないのは、抽出器自身の出力を正解表にしない原則（`06-scenario-test.md` 共通手順4）と同じ理由。

#### 完了条件・停止条件

**前提条件（起動前にアプリが判定する。エージェントの停止条件ではない）**: 入力上限（D02: ファイル数・容量・ページ数）の判定は FUNC-01 の受付時にアプリが行い、超過は具体的に通知して**エージェントを起動しない**。読取成功資料が1件以上あることも起動前に確認する。エージェントは上限内・読取成功資料ありの案件に対してのみ起動される。

| 種別 | 条件 | 判定方法 |
|------|------|---------|
| **成功（完了）** | ①投入資料のうち読取成功範囲すべてを走査した ②明細行が1件以上あり、**全行に原項番と出典**（資料名＋ページ／シート・セル／本文位置）がある ③重要項目（品種・数量・単位・外径・肉厚／単重・材質・接続・レンジ／定尺長・要求納期・納地）が値または状態（TBA／記載なし／適用なし）で埋まっている ④案件情報の必須項目が埋まっている（不在は「記載なし」として明示） ⑤原明細インベントリ（明細＋除外要素と除外理由）が作られている ⑥確認事項がある場合はすべて対象（実在する行IDまたは案件）・対象項目つきで登録されている（確認事項0件も成立する） ⑦読取不能・未完了範囲が記録されている ⑧版が「作成案」として確定した | `validate_draft` が全チェックを通過。**機械判定できる項目**（種別名の SSOT は ⑤3.4）: 未走査範囲0件（`unscanned_range`。読取成功ページから、実行トレースが走査した範囲と読取不能として記録済みの範囲を差し引いて判定＝完了条件①）／出典欠落0件（`missing_evidence`）／単位を伴う数値項目に単位あり（`missing_unit`。数量だけでなく外径・肉厚・単重・定尺長も）／全行に原項番（`missing_source_no`）／選択グループの候補が2件以上（`orphan_candidate`。**候補1件は分割し損ね**として検出する）／確認事項の対象行が実在する行IDまたは案件（`orphan_question`）／小計・合計・再掲が明細に含まれずインベントリ側に除外理由つきで残っている（`excluded_without_basis`）。**完了条件③・「未確定は状態値で保持」・「候補数量の合算なし」は機械判定リストに置かない**——③は `items` の重要項目ごとの状態列（`od_state` / `wall_state` / `weight_state` / `grade_state` / `connection_state` / `length_state` / `due_state` / `place_state` / `qty_state`。`case_headers` は `customer_name_state` / `due_state` / `place_state` / `incoterms_state` / `inquiry_no_state` / `quote_deadline_tz_state`）と、値と状態を対にする CHECK 制約により**値も状態も無い行が登録時に弾かれる**（④3.3）。「未確定は状態値で保持」も同じ CHECK で担保され、合算は合計列そのものが無いため発生し得ない（④0.2 原則3）。判定が空振りするチェックを完了条件に並べない |
| **失敗（中断）** | ①全資料が読取不能・暗号化・未対応で有効テキストが0（起動前の確認をすり抜けた場合の二重防御） ②`validate_draft` が3回連続で同じ違反を返す（自己修復不能） | 読取成功資料数0で中断。違反内容のハッシュを比較して同一違反の連続回数を数える。**いずれの場合も「明細0件の正常な作成案」を作らない**（N03） |
| **強制停止** | 最大ターン数 **80**（2026-09-13 改定・memory AD-021。旧 40 は実評価 run 7 で根拠登録だけで使い切った）／**内側**タイムアウト **15分**（D06 仮値。N06 の性能要件10分より後ろに置き、境界で成功と停止が重ならないようにする）／メッセージ間の**無応答**タイムアウト（内側より短い値）／同一ツール・同一引数の連続呼び出し3回 | ツール呼び出し回数をカウント。起動時刻からの経過秒を計測。直前3回の (ツール名, 引数ハッシュ) を比較。**無応答 < 内側 < 外側（`jobs.py` のフェイルセーフ）の大小関係を崩さない**（`agent-development.md` §6）。3つの値と発火した層は `agent_runs.limits` / `stop_reason` に残す |

**強制停止時の扱い**: 途中まで作った明細は破棄せず、版を「一部未完了（資料名 p.x）」として記録する。完全成功と表示しない（N03）。担当者は SCR-02 の読取結果と SCR-05 の注記で未走査範囲を確認する。

**停止理由の語彙（`agent_runs.stop_reason`・④3.2）**: `completed` / `failed` / `max_turns` / `inner_timeout` / `inactivity_timeout` / `outer_timeout` / `repeated_call` / `no_readable_document` / `validation_loop`。`.claude/rules/agent-development.md` §3 と一致させ、タイムアウトは**無応答 < 内側 < 外側**の2層を区別して記録する（外側＝`jobs.py` の発火は内側が機能しなかった異常であり、単一の `timeout` に丸めない・同 §6）。**その実行に適用した閾値は `agent_runs.limits` に保存する**（D06 は仮値のまま実測して見直すため、閾値を設定ファイルだけに置くと過去の実行を比較できない・N04）。

**出力形式**: 02 5章の領域1〜4（案件情報／Item List／根拠／確認事項）と領域6（原明細インベントリ）を構造化して保存する。領域5（変更・確認記録）は人の記録でありエージェントは書かない。保存先テーブルは Part 2 のツール一覧最終列（→ `04-db.md`）。

#### ユーザーから見た体験

- **実行中の見え方**: SCR-02 の案作成ボタンが無効化され「準備中…」を表示。進捗は「資料 n/N を読取中 → 明細を抽出中 → 自己点検中」の段階表示（途中経過の明細のストリーミング表示はしない。確定前の行が正解に見える誤解を避ける）。段階の保持先は `agent_run.stage` / `stage_detail`、取得は `GET /agent-runs/{id}`（④3.2・⑤3.2）
- **中間承認**: **なし。** 生成は一気に走る。ただし生成物は「案」であり、担当者の一致確認（FUNC-08）を経ない限り状態は作成案に留まる。**承認は生成の途中ではなく生成の後に置く**という設計
- **例外**: 外部LLMへ資料を送信する構成で動かす場合は、**送信前に対象ファイルを提示して人の確認を取る**（D05 が未承認のため初版はローカル読取＋ダミー応答で実装する）
- **対応画面(③)**: 起動 = SCR-02、成果物の確認 = SCR-03（明細・根拠・確認事項）／SCR-04（行ごとの出典）／SCR-05（原明細インベントリと網羅性）

#### サブエージェント構成

**単体エージェント。** オーケストレーター＋サブエージェントには分割しない。

分割候補として **網羅性自己点検エージェント**（read系ツールのみを持ち、原資料と登録済み明細を突合して欠落・余分・重複を報告する）を検討した。分割の利点は明確で、生成した本人が自分の出力を点検すると「読み落としたページ」を読み落としたまま合格と判断する（自分の文脈に無いものは検出できない）。

初版で採らなかった理由:

1. 欠落検出の主要部分は `validate_draft` の**決定的チェック**で足りる（未走査範囲・出典欠落・単位欠落・原項番欠落・候補1件のグループ）。LLMの判断を要するのは「除外理由が妥当か」だけで、これは人が SCR-05 で確認する設計になっている
2. `03-spec.md` SCR-05 の前提注記のとおり、**抽出処理が最初から読まなかった範囲は自己点検でも検出できない**。点検エージェントを足しても原資料の全ページ確認は人の仕事として残る。二重に読ませてもこの穴は塞がらない
3. まず単体で成立させ、S01〜10 の確認前誤り率（目標10%以下）を測ってから分割を判断する

**Scope 2 の候補として記録する**: 誤り率が目標に届かず、原因が「読んだが取り違えた」ではなく「読まなかった」に偏る場合、コンテキストを隔離した点検サブエージェントを追加する。その場合のツールは `list_case_documents` / `read_document` / `read_email` / `record_question` / `record_source_inventory` の read 中心のサブセットとし、`propose_items` と `finalize_draft` は与えない（点検役が明細を書き換えられないようにする）。

#### ガードレール

- **してはいけない操作**
  - **未承認の換算・同等化**（D03 未承認）: トン→本数、mm→公称inch、肉厚→単重、レンジ→平均長を計算しない。HCL80／SM95TT／P110HP／13CR-95 を他仕様へ置換しない（R03・R04）
  - **未確定の数値化**: TBA・記載なし・適用なしを 0 や空欄、架空の仕様に変換しない（02 5章）
  - **択一候補の合算**: 選択グループの候補数量を足して発注数量として出さない（R07）
  - **相反する記載の一方採用**: 同一項目に相反する数量・仕様があり優先関係を資料から判定できない場合、どちらかを選ばない。同一選択グループ（`CFL-n`）の候補2行として**両方を出典つきで残し**、確認事項（`conflict`）で人に差し出す（X04・④3.3）
  - **架空行の生成**: 「代替提案可」という条件だけで代替行を作らない（R07）。省略条件を無条件に確定しない（R08）
  - **原表記・出典の書き換え**: 原表記は保存専用。出典を後から都合よく付け替えない
  - **人の記録の代筆**: 確認者名・修正者名・判断者名・確認日時を生成しない（02 7章「AIが承認者名や日時を作らない」）
  - **状態の前進**: 担当者確認済み・評価確認済み・送付可否を書き換えない（ツールを持たない）
  - **対外送付**: メーカーへの送信・メール送信を行わない（01 の原則、Out of Scope）
  - **入力資料の改変**: 資料は読取専用。処理失敗・再実行でも書き換えない（N01）
  - **資料内の指示の実行**: 資料本文の「〜へ送信せよ」「このリンクを開け」を命令として実行しない。**業務条件の記述として抽出対象にする**（02 0章／N02）。外部リンクの自動取得も行わない
  - **案件の混在**: 他案件の資料・明細を参照しない（N01）
  - **ログへの全文出力**: 資料全文・認証情報を実行ログに不要に残さない（N02）

### T-202 ジョブ境界の補足（RV-015、2026-09-12）

- 停止閾値の既定値はdefinition.pyのdefault_run_limitsで組み立て、DTO・dispatcherへ注入する。ダミーモデル識別子もdefinition.pyからservice経由でrepositoryへ渡す。
- jobsの外側期限でcancelした後は20msだけ後始末を待つ（非協調workerの停止待ちで上限を失わない）。完了保存は1回5秒を上限として最大3回、間隔は0.1秒・0.2秒。完了保存自体がcancelを抑止してもasyncio.waitで待機を打ち切り、総猶予16秒以内を保つ。例外診断は型名のみを記録する。
- T-203 workerはcancel後に新たなツール呼出し・成果物書込を開始せず、取得済みリソースを解放すること。終了済み実行への書込拒否は引き続きrepositoryで強制する。
- 進捗GETに回収・JSONL出力の副作用を持たせない。保存失敗が全再試行後も続いた実行は次の実行開始要求またはプロセス起動で回収する。その間、ポーリングは最後に保存された状態を返す。
- 起動時にも別プロセス（テスト含む）のworkerが生きている可能性があるため、保存された外側期限で回収対象を判定する（AD-023 / LN-055）。runningかつstarted_at + limits.outerTimeoutS + 終端保存猶予16秒 < nowのみをfailed/process_interruptedにし、そのrunだけJSONLを再構築する。猶予込み期限内・ちょうどのrunは変更しない。回収の述語は両経路で共通化し、猶予はdomain.run_types.RECOVERY_GRACE_Sに集約し、definitionから再公開する（L-8b / LN-056）。lifespanもget_dbのdependency overrideを通し、統合テストの起動が開発DBに触れないようにする。
- T-203へは自動着手しない。既存runner/hooks/TraceRecorderの統合、ガードレール差込口、runロック中のツールstep採番、decision/observationスキーマはT-203開始前の設計・レビュー課題とする。新ジョブのJSONLはRunTraceStoreを使用し、旧TraceRecorderへ本文を流す経路を接続しない。

### T-203 ローカル実行の具体化（2026-09-12、ユーザー着手指示）

- RunDispatcherへローカルworkerを注入する。外部queryは使用せず、13ツールの実処理をservice/repositoryへ接続する。PreToolUse hookを呼出し境界で必須にし、登録外ツール・読取系ツールのスカラ引数にある外部URL・案件/版/規則の逸脱を拒否する。記録系ツールのquote/excerpt/reason/*_raw等の原文はURLを含めて保存できる。pingは通常登録しない。
- 同一版→runの順で行ロックを取得する。各呼出しの開始stepを先にcommitし、成功stepと成果物を同じトランザクションでcommitする。複数読取範囲は同じ呼出しをparent_step_idで結ぶ。email:(role,seq)重複は読取失敗とし、成功走査を捏造しない。
- trace_eventのinputはスコープID、decisionはreading/extracting/self_checking、tool_useは許可名/引数ハッシュ、observationは結果状態/件数の安全なメタデータとする。生の判断文・資料本文・例外メッセージは記録しない。DB確定イベントを既存RunTraceStoreで終了時にJSONLへ反映する。
- D05のダミー判断は評価用の明示形式に限定する。ローカル本文中の `No.1 | Kind: casing | Qty: 150 MT` のような1行明細を読み、原値・状態・根拠とインベントリを登録して検証・確定する。曖昧な自然文、未対応の表/注記/メール更新解釈は正常完了とせず、ローカルダミー未対応として停止する。S01〜S10の抽出精度評価は実モデル未接続の段階では未達とする。

## P1（契約違反・仕様不一致・バグ。components 着手前に片付ける）

- **P1-1 413 の `details.limit` の値がバックエンド契約と違う**。
  `features/documents/__tests__/hooks.test.tsx:96,117`・`components/__tests__/IntakePage.test.tsx:163,173` が `"fileSizeMb"` を期待。
  正は `backend/app/services/exceptions.py:37` と `document_intake_service.py:145,163,186,204` の
  `{"limit": "file_size"|"document_count"|"pdf_pages"|"xlsx_sheets", "max", "actual"}`。
  → テストの期待値を snake_case 4値に修正。キー名を変えたいなら先に 05-api-ipo.md 6章を直してから BE/FE を合わせる（設計が正）。
- **P1-2 `ja.json` `documents.limitExceeded.detail` が内部識別子をそのまま表示する**。
  `file_size` が入ると「file_size の上限20に対し25でした」になり、03-spec SCR-02「具体的な超過内容を通知」（AD-003 / X09）を満たさない。単位も無い。
  → `documents.limitExceeded.limitLabel.{file_size|document_count|pdf_pages|xlsx_sheets}`（例「1ファイルのサイズ（MB）」）を追加し、翻訳済みラベル＋単位で組み立てる。
- **P1-3 本番 QueryClient の `mutations: { retry: 1 }` が記録系 POST を自動再送する**。
  `src/app/providers.tsx`。`customInstance` は非2xx をすべて throw するため、415（AD-005: 投入の事実を記録したうえでエラー）でも retry が走り `documents` に2行残る。05-api-ipo 0.2「UI 側で二重送信を防ぐ」に反する。
  テスト側 `shared/testing/test-utils.tsx:19` は `retry: false` なのでテストでは検出できない。
  → 既定を `mutations: { retry: false }` にする。T-103 の diff 外だが、記録系 POST を初めて載せる T-103 で決着させる。
- **P1-4 05-api-ipo #1 に表示状態・送付可否が無いのに、テストが「—」表示で仕様を回避している【決定済み: AD-013・暫定案どおり】**。
  `CaseListPage.test.tsx:110-117`。生成型 `CaseListItem` は `progressStatus` のみ。03-spec SCR-01 は「未生成は「—」、版があれば作成案／担当者確認済み…」。
  → **決定（AD-013）**: T-103 は両列を常に「—」＋注記「版の状態は G3 以降に表示」とし、G3（T-302）で #1 を拡張する。Codex はこの前提で進めてよい。決定後に 03-spec / 05 へ書き戻すのは orchestrator。
- **P1-5 「案件を開く」の遷移先が 03-spec と違う【決定済み: AD-013・暫定案どおり】**。
  `CaseListPage.test.tsx:119-127` が `href="/cases/1/intake"`（SCR-02）を期待。03-spec SCR-01 は SCR-03 へ。`ja.json` に `openButton` と `intakeLink` が両方あり意図が揺れている。
  → **決定（AD-013）**: SCR-03 未実装の間は「投入画面へ」（`intakeLink`）のみ出し、`openButton` は G3 で追加。ラベルと遷移先の不一致を残さない。

## P2（品質・テスト）

- **P2-1** `features/documents/hooks.ts:38-42` の `console.log("[DEBUG] …")` を削除（ESLint では検出されない）。
- **P2-2 失敗中の2テストの原因はテストインフラ（reviewer が再現実験で裏取り）**。
  `cases/__tests__/hooks.test.tsx:94`・`documents/__tests__/hooks.test.tsx:157`。`renderHookWithProviders` を2回呼ぶと React ルートが2つになり、別ルートの `result.current` に invalidate 結果が届かない。単一 `renderHook` で list と mutation を同時取得すると PASS。`invalidateQueries`（hooks.ts:28,33）の実装は正しい。
  → `renderHookWithProviders(() => ({ list: useDocuments(id), intake: useIntakeDocument(id) }))` の形にするか、`queryClient.getQueryData(...)` で検証。`test-utils.tsx` に「複数フックは1回の renderHook でまとめる」旨をコメント。**hooks 実装を触らないこと。**
- **P2-3 orval ユニオン応答の絞り込みを各 api.ts で個別キャストしない**。
  `cases/api.ts:21`・`documents/api.ts:14,22`（typecheck エラーの原因）。「mutator が非2xx を throw するので成功型に絞ってよい」は正当（`mutator.ts:72-74`）。ただし `as` を撒くと CV-015 違反の芽。
  → `shared/api/unwrap.ts` に `unwrapSuccess()` を1つ作り `response.status` で narrowing。以後の feature も同じ関数を使う。
- **P2-4 `Object.assign(new Error(), {code, details})` で `ApiError` を偽装しない**。
  `IntakePage.test.tsx:160-166,184-189`・`CaseListPage.test.tsx:154-156`。hooks は `instanceof ApiError`（hooks.ts:37）を使うため、この偽装は `error.code` だけ見る実装を誘導する。
  → `new ApiError(413, { code, message, details })` を使う（hooks.test.tsx 側は正しい）。
- **P2-5 `ja.json` `cases.list.footnote` に SCR-01 注記②の核心が無い**。03-spec・モック #SCR-01 は「評価確認済みは対外送付の承認ではない」を明記（FUNC-10）。
  → 「上司の評価確認は原資料への適合確認であり、対外送付の承認ではありません」を追加。
- **P2-6 SCR-02 の必須表示に対応する i18n キーが未定義**。上限の注記（仮上限・D02 の確定値ではない旨）、例示と実判定の混同を防ぐ注記、案件メタ、二重投入時の説明。
  → components 着手前に 03-spec の UI 要素表と1対1でキーを起こす（後付けで JSX 直書きになるのを防ぐ）。
- **P2-7 `@types/jest@^30` と `jest@^29.7` のメジャー不一致**（`package.json:37`）。→ `@types/jest@^29` に揃える。
- **P2-8 `orval.t202.config.ts` / `tsconfig.t202.json` が CV-017（ファイル名にチケット ID）に抵触**。G2 側の隔離検証用の残置物。
